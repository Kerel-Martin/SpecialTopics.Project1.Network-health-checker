Network Health Checker — Final Report

Special Topics, Project 1 · Kerel Martin Fahim and Cynthia Ziadeh · 16 November 2026
Repository: https://github.com/Kerel-Martin/SpecialTopics.Project1.Network-health-checker

1. Problem and goal

To see which devices on a small network respond, you usually ping each address by hand, one at a time. With many devices this is slow, and the results are easy to lose. Our goal, set in the approved SPEC.md, was a Python application for students and home users. It loads a text file of up to 20 candidate IPv4 addresses (R1) and marks the invalid ones (R2). It pings every valid address and reports it as UP or DOWN (R3) with its response time (R4). A scan of 20 addresses must finish within 5 seconds (R5). The results can be exported to CSV (R6), and the app prints summary counts (R7). The required platform is Windows, and the required interface is the command line.

Ping uses ICMP echo requests and replies [8]. A DOWN result therefore means only that no reply arrived within the timeout, not that the device is off: a firewall may simply drop ping. Discovering devices automatically, scanning ports, and monitoring continuously are out of scope.

2. Design

Figure 1. How a scan flows through the modules in src/network_health_checker/. Solid arrows show data; dashed arrows show INVALID entries skipping ping, and the R5 test calling the scanner repeatedly.

How it works. loader.py reads the file and enforces the limit of 1–20 entries. It skips blank lines and accepts files saved by Windows Notepad. validator.py checks each entry with Python's ipaddress module [1], which rejects octets above 255, the wrong number of octets, text and leading zeros. scanner.py passes only VALID entries to a ThreadPoolExecutor [3], so all the pings wait in parallel. A scan of 20 addresses therefore takes about one timeout (1 s by default) rather than one timeout per address.

pinger.py runs the operating system's own ping through subprocess [2, 6, 7]. We chose this over raw ICMP sockets, which need administrator rights. The cost is that the program must read ping's text output. It counts a reply only if the output contains a TTL= value. This holds in any system language, and it avoids a Windows trap: a router answering "Destination host unreachable" makes ping exit with code 0. The response time is read from the reply line, and a reply slower than the timeout counts as DOWN (the fix for Bug 2).

The command-line interface (cli.py, the interface the spec requires) and the optional Tkinter window (gui.py) [5] share the same code. The GUI runs scans in a background thread and receives the results through a queue, so the window never freezes. Its buttons run the AC5 test (performance.py) and the CSV export (exporter.py, using Python's csv module [4]). The ping function is passed in as a parameter, so tests can replace it with a fake that gives fixed answers. Real-ping tests use only 127.0.0.1 and 192.0.2.x, a range reserved for documentation that never replies [9]. The application is 717 lines of standard-library Python; the tests are 1,193 lines.

Bugs found and fixed (bug log in TESTING.md, section 3). Bug 1: under pytest on Windows, GUI tests were skipped at random, and the AI-written skip message wrongly blamed "no display". The cause was pytest's file-level output capture; the fix was --capture=sys in pytest.ini [12]. Bug 2: a reply arriving after the timeout was reported as UP, which contradicts R3. With --timeout 10, 8.8.8.8 showed "UP 43 ms", because Windows ping -w still prints late replies. The bug was in AI-written code, and it was fixed by applying the timeout to the measured time. Its regression test fails on the old code and passes on the new code; we checked this on both operating systems.

4. Limitations

  • DOWN does not mean offline. Windows blocks incoming ping by default. Our second laptop was DOWN until we added a firewall rule [13], and another device (192.168.18.17) answered at the network level but never replied to ping.
  • One ping per address. There are no retries, so a single lost packet gives DOWN, and the response time is a single sample. On Wi-Fi, power saving made times vary from about 3 ms to 397 ms, and a device that was asleep (192.168.18.225) was DOWN in one scan and UP in a later one.
  • Accuracy: on Windows, replies faster than 1 ms are recorded as 1 ms (an error of at most 1 ms, measured). On Linux, ping -W takes whole seconds, so a timeout below 1 s still waits up to 1 s. Late replies are still filtered out, but the scan is no faster.
  • It depends on ping's text output. We tested English Windows, a German Windows sample and Linux iputils ping. Other languages or ping versions might format replies differently. macOS is supported in the code but was never tested.
  • The performance figure is local. AC5 was measured on one home network with exactly 20 addresses. As SPEC.md says, it is not a guarantee for every network.
  • Scope: IPv4 only, at most 20 addresses, no continuous monitoring. The GUI was tested with automated smoke tests and by hand, not with real users.

5. Discussion

What we learned. The clearest lesson was the gap between working code and correct code. Bug 2 sat in code that had passed every test and many real scans for two weeks. It only showed up when we deliberately tried an extreme case (a 10 ms timeout) and compared the app with Windows' own ping. Tests check only what you think of testing, and comparing with an independent tool finds what you did not think of. We learned the same about measurements: an AC5 run that was too fast (0.25 s against a 1 s timeout) was a warning sign, not good news. Recording the test conditions is what showed the run was invalid. We also learned the difference between a valid address and a reachable one, why a firewall can hide a device from ping, and how much small platform differences matter: Windows ping exiting with 0 for unreachable hosts, py versus python3, Tkinter missing by default on Ubuntu, and pytest's output capture interfering with Tkinter. Finally, an AI assistant produced code quickly, but it also introduced both bugs we found. We had to understand and verify every part ourselves.

What we would do differently. We would write the acceptance tests in pytest, named after AC1–AC7, from the first prototype instead of adding them in Milestone 3, and compare with a reference tool early. That would have caught Bug 2 a milestone sooner. We would put the GUI in the specification from the start instead of recording it as a change afterwards. We would send two or three pings per address and report packet loss, so that Wi-Fi devices are not marked DOWN after one lost packet. And we would share the implementation work, and the commits, more evenly between the two of us. Most of the commit history is Kerel's, and Cynthia's commits come mainly from the Windows testing in Milestones 2 and 3.
